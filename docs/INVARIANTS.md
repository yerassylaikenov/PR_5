# Инварианты реестра (PR5)

Инварианты сформулированы как **булевы свойства состояния** и проверяются
автоматически в `test/invariants/registry-invariants.test.ts` после случайных
воспроизводимых (seeded) последовательностей действий, а также частично в
property-тестах `test/property/`.

## INV-1 (OWASP SC01) — авторизация

**Состояние реестра изменяют только держатели соответствующих ролей.**
Для любого адреса `a`, не имеющего роли, и любой функции записи `f`
(`registerPayment`, `cancelPayment`, `markExecuted`, `markRejected`, `pause`):
вызов `f` от имени `a` завершается откатом (`AccessControlUnauthorizedAccount`),
и наблюдаемое состояние (`totalRegistered`, все `getPayment`) не меняется.

- Проверка: в каждом шаге инвариант-теста посторонний адрес пытается
  `registerPayment` → ревёрт, `totalRegistered` до = после.
- Также: property P2 (любой случайный адрес без роли не может писать).

## INV-2 (OWASP SC03) — неизменяемость и финальность

**Финальный статус необратим, а ключевые поля неизменны после регистрации.**
Для любого `paymentId`:
- если `status ∈ {Executed, Rejected, Cancelled}`, то он больше никогда не меняется;
- `docHash`, `amount`, `registeredBy` после регистрации не изменяются никаким
  вызовом.

- Проверка: ghost-модель сравнивается с `getPayment` на каждом шаге —
  `docHash`, `amount`, `registeredBy` всегда совпадают с зафиксированными при
  регистрации; из финального статуса переходы откатываются
  (`InvalidStatusTransition`, integration т.6).

## INV-3 (OWASP SC01/SC03) — «4 глаза» и счётчик

**Для любого исполненного/отклонённого поручения исполнитель ≠ инициатор, а
счётчик равен числу успешных регистраций.**
- Для любого `paymentId` со `status ∈ {Executed, Rejected}`:
  `settledBy != registeredBy`.
- `totalRegistered == |{ paymentId : status != None }|` (число успешных
  `registerPayment`).

- Проверка: на каждом шаге для финальных статусов проверяется
  `settledBy != registeredBy`; по завершении последовательности
  `totalRegistered` сверяется с числом успешных регистраций в ghost-модели.

## Почему выбран TypeScript + ghost-модель

Инварианты реализованы на TypeScript (node:test + viem) со случайным
seeded-сценарием и ghost-моделью, а не на Solidity. Это **проще** для учебного
стенда (единый стек с интеграционными/ property-тестами, без forge-std), даёт
читаемую диагностику при расхождении и переиспользует общие хелперы. Семантика
та же: последовательность легитимных действий + попытки постороннего адреса, а
после каждого шага — проверка булевых свойств состояния.
